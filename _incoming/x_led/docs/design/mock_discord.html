Annotation · design rules — timestamps, indicative odds, one rake

Discord does not parse <t:…> tokens inside an embed footer. A competitor ships the raw token there. The live relative time lives in the description, where Discord does render it (highlighted above, “in 2 days”), and the footer carries a plain absolute string that needs no parsing.

Odds are labelled indicative in the embed body, not in a tooltip nobody opens. Bars are unicode blocks because embeds cannot carry styled graphics; that is the honest medium. Every figure sits in inline code, so Discord renders it in a mono face and pots, percentages and odds line up in columns.

Annotation · design rules — modals hold text only, never identity

A Discord modal cannot hold a select or an autocomplete, and takes at most 5 text inputs. So the only thing the user types is the one thing only they know: the amount. The market and the outcome arrive from the button that opened the modal, not from a field asking for an ID.

The submit button says Preview stake, not Place stake. Nothing has touched the wallet yet.

The outcome field is pre-filled, not read-only — Discord has no read-only flag on a TextInput. A modal always returns whatever the user left in the box, so on submit the handler re-validates the outcome string against the custom_id of the button that opened the modal (estates:market:63:stake:ashfall) and rejects a mismatch. It also re-resolves market #63 from the message id before doing anything, because after a restart a persistent view comes back with placeholder state.

Annotation · design rules — preview by default, claim-first, caller-minted keys

Users confirm numbers, not intentions. The preview shows the exact before/after on both sides: what happens to their wallet and what happens to the market. Applying is a separate, explicit press.

Money uses three colours with fixed meanings: available is primary text, held is amber, debt would be red. Balance is unchanged, because a hold reserves rather than spends, and the copy says so in words too.

The idempotency key estates:market:63:stake:2418 is minted from the domain event at preview time and reused on every retry of the confirm. It is not a fresh uuid4() per HTTP attempt. Pressing Confirm twice, or a network retry, produces one hold.

On confirm the bot marks the wager row claimed in one UPDATE … WHERE state='pending', and only calls /hold if it won the row. If the hold fails, the row is released back.

Annotation · design rules — hold/release is visible, empty states stay empty

Same escrow machinery as betting: a bid is a hold, being outbid releases it, winning captures to treasury:estates and then transfers hammer minus 3% to the seller. The user is told in plain words that their money came back, because a silent release looks like a loss.

Bid min (19,400) exists so the common case needs no modal at all. Bid opens the same amount-only modal as staking.

If the user had no position on this lot, the “Your position” block would be absent, not present-and-saying-zero. Absence is not decorated.

Every button re-resolves lot #425 from the message id before acting, so a bot restart cannot make “Bid min” bid the wrong number on a stale view. Five buttons is one full action row — Discord's maximum per row, five rows per message.

Annotation · design rules — four slash commands, not forty

The whole bot's command surface is /estates, /bet, /lot, /parcel. Everything else is a button on a panel. Restocker went from 136 commands to ~15 for exactly this reason, and Estates ships small from day one instead of being cut back later.

Panels are 5 rows × 5 components, so this fits with room to spare. Views cannot hold free text, which is why the Jump to… row is a select and never a “type a lot number” box.

Held coins are itemised on sight. A user should never have to ask why their available is lower than their balance.

If core is down the panel refuses to open rather than showing a cached or optimistic number. Coins live in one place; when that place cannot be reached, Estates does not guess.

Annotation · design rules — two-step gate, integer money, compensating reversal

resolve(proposed) → confirm(pays out). A competitor resolved a market to the wrong outcome after payouts had started and had to walk it back publicly. Here a single misclick cannot pay 60k: the Confirm button is disabled for the hold-down, and Unresolve before confirm is free.

The staff member confirms the exact table that will execute, down to the per-row idempotency keys, not a sentence saying “resolve this market”.

All integer arithmetic: stake × distributable // winning_pool, the same expression the stake preview shows. Payouts sum to 87,399 and the 1-coin remainder is stated on screen as going to the treasury. No floats anywhere on this path.

So the button says 87,399, not 87,400. 87,400 is the distributable; 87,399 is what actually leaves in transfers, and the missing coin is the floor remainder named in the table. A confirm button is the last figure anyone reads before coins move, so it is the one figure that must not be rounded up to a friendlier number.

Payouts advance the progress marker per row, not after the loop. Each transfer is claimed with UPDATE … WHERE paid_at IS NULL first and only sent if the row was won.

After confirm there is no delete. A reversal is a compensating run with keys estates:market:63:reverse:user:<uid>, which fails loudly if a winner already spent the coins rather than pushing a wallet negative. Every run posts itself to #payout-proof, so the proof cannot be forged by omission.
